CYBERNET LAB - MASTER REBUILD BLUEPRINT
========================================
Version: 1.0
Purpose: A complete implementation contract for rebuilding CyberNet Lab from zero.
Audience: An AI coding agent, product engineer, or development team.
Language: English technical specification with simple wording.

IMPORTANT IMPLEMENTATION RULE
-----------------------------
Do not build a visually impressive fake simulator. Build only behavior that is
implemented, testable, and explainable. If a protocol, command, device behavior,
verification method, or topology is not supported, label it clearly as unsupported
or conceptual. Never return fake success, invented output, invented devices, or
invented packet behavior.

This document is the source of truth for the rebuild. Before writing code, the
implementer must convert this document into a tracked task list and a traceability
matrix. Every feature must have: data contract, UI location, runtime behavior,
error state, test, and documentation.


1. PRODUCT PURPOSE
------------------
CyberNet Lab is a beginner-to-advanced practical learning platform for computer
networking, network engineering, defensive security, and automation.

The platform must teach this complete engineering loop:

  understand the problem
  -> inspect the topology and current state
  -> predict the expected behavior
  -> plan a safe change
  -> configure one controlled change
  -> verify from evidence
  -> troubleshoot the first failed check
  -> fix and verify again
  -> document the result and rollback

The product is not only a command reference. It must teach reasoning, evidence,
communication, and safe operational practice.

Primary users:
  A. New student with no networking experience.
  B. Beginner who knows basic IP and wants guided labs.
  C. Intermediate student preparing for practical networking work.
  D. Advanced learner practicing routing, security, observability, and automation.
  E. Instructor or mentor who needs reliable progress and evidence.

Primary constraints:
  - Windows, macOS, and Linux development.
  - Low-resource browser-first mode.
  - No requirement for real hardware for beginner labs.
  - Real emulator/container support only when the host can support it.
  - Safe isolation for security labs.
  - Honest simulator limits.
  - Accessible UI and keyboard operation.


2. RESEARCH PRINCIPLES TO FOLLOW
---------------------------------
Use these principles in product and curriculum decisions:

1. Progressive fidelity:
   Start with deterministic browser simulation. Later offer protocol simulation,
   emulators, containers, and VMs. Do not pretend a browser model is a real IOS.

2. Outcomes before tools:
   A learning objective must remain meaningful even if the student changes from
   Packet Tracer to GNS3 or another backend.

3. Active learning:
   Every important activity should follow:
   predict -> perform -> observe -> explain -> retry -> reflect.

4. Evidence-based troubleshooting:
   Grade diagnosis, evidence, safe change, verification, and documentation, not
   command memorization or speed alone.

5. Universal access:
   Target WCAG 2.2 AA. Provide text alternatives to diagrams, keyboard controls,
   readable contrast, terminal font controls, and no unnecessary time pressure.

6. Role-based engineering:
   Map advanced outcomes to NIST NICE roles and skills. Map selected security
   labs to MITRE ATT&CK techniques without treating ATT&CK coverage as a checklist.

7. Japanese practical pattern:
   Include recurring incident "fire drill" exercises, role-play, mentor feedback,
   iteration, and long-running build projects. NICT CYDER and SecHack365 are
   reference patterns. Do not make unsupported cultural claims about China;
   obtain primary Chinese-language education sources before localization.

3. CURRICULUM AND LEARNING LEVELS
----------------------------------
Do not expose hundreds of ungrouped labs as the default learner experience.
The catalog may contain many labs, but the learner sees a guided path first.

LEVEL 0 - DIGITAL AND CLI FOUNDATIONS
  - Files, folders, browser, terminal, copy/paste, screenshots.
  - Windows and Linux network commands.
  - Decimal, binary, hexadecimal, bits, bytes.
  - What a device, interface, cable, IP, MAC, and port are.
  - Authorization, lab safety, and responsible use.
  - Assessment: identify a device/interface and explain a simple command.

LEVEL 1 - NETWORKING FOUNDATIONS
  - Ethernet and switching.
  - IPv4 structure and subnet masks.
  - Same-subnet communication.
  - Default gateway.
  - ARP and ICMP.
  - Ping and traceroute concepts.
  - Interface status and basic topology.
  - Assessment: build a two-host network and prove connectivity.

LEVEL 2 - SWITCHING
  - VLANs, access ports, trunks.
  - Native VLAN concept.
  - Inter-VLAN routing.
  - MAC address table.
  - STP purpose and safe verification.
  - EtherChannel concept.
  - Port security.
  - Assessment: isolate departments and verify intended reachability.

LEVEL 3 - ROUTING
  - Connected, static, and default routes.
  - Routing table interpretation.
  - OSPF concepts, neighbors, areas, and route selection.
  - EIGRP/RIP only when the selected backend actually supports them.
  - Route failure and convergence concepts.
  - Assessment: repair a multi-network topology and provide evidence.

LEVEL 4 - SERVICES
  - DHCP DORA.
  - DNS resolution.
  - NAT/PAT.
  - NTP, syslog, SSH.
  - HTTP/service reachability.
  - Service failure troubleshooting.

LEVEL 5 - SECURITY FOUNDATIONS
  - Authentication and authorization.
  - Secure management.
  - ACL logic and first-match behavior.
  - Segmentation and least privilege.
  - Port security and logging.
  - Safe scanning only inside an isolated authorized lab.
  - Security incident evidence and containment.

LEVEL 6 - ADVANCED ENGINEERING
  - Multi-site routing.
  - Redundancy concepts only if simulated truthfully.
  - VPN concepts.
  - QoS concepts and measurement.
  - IPv6.
  - Network automation, JSON/YAML, APIs, Ansible concepts.
  - Config backup, diff, rollback, Git workflow.
  - Packet capture and protocol analysis.

LEVEL 7 - PROFESSIONAL CAPSTONE
  - Ambiguous ticket or incident.
  - Multiple plausible causes.
  - Hidden seeded fault.
  - Evidence collection.
  - Smallest safe fix.
  - Independent verification.
  - Root-cause report, prevention, and stakeholder summary.

Mastery gates:
  - A learner may open any lab, but the UI must show missing prerequisites.
  - Recommended path requires passing the previous gate.
  - Gates must test transfer to a new topology, not only repeat the same steps.
  - A gate records attempts, hints, verification evidence, and explanation quality.

8. RUNTIME ARCHITECTURE
-----------------------
Use one authoritative runtime state per session.

Recommended layers:

  frontend/
    app shell and views
    feature modules
    accessible components
    API client
    WebSocket client

  domain/
    canonical lab model
    state machine
    command contracts
    verification contracts
    scoring contracts

  simulation/
    browser deterministic simulation
    protocol models
    packet/event model
    device adapters

  workers/
    container/VM/emulator orchestration
    never run untrusted lab workloads in the web process

  backend/
    REST API
    WebSocket session events
    session ownership
    lab catalog
    verification service
    evidence service
    telemetry

State rules:
  - One session has one authoritative device state.
  - UI state is a projection, never a second source of truth.
  - Every state mutation has an event and timestamp.
  - Reset restores a versioned initial snapshot.
  - A command result includes command, target, mode, output, state change,
    verification impact, and error category.
  - Backend and frontend use the same verification contract.

Avoid:
  - three competing device stores;
  - verification that always returns success;
  - UI-only progress;
  - command handlers that are registered but not used;
  - dead duplicate components without an archive note.

10. VERIFICATION AND SCORING
----------------------------
Verification types:
  - cli_output
  - state_check
  - topology_check
  - interface_check
  - addressing_check
  - route_check
  - ping/connectivity
  - service_check
  - configuration_diff
  - evidence_submission
  - reflection

Every verifier returns:
  passed
  verifierVersion
  message
  expected
  actual
  evidence
  affectedDevices
  hint
  limitations
  score

Verification must fail safely:
  - missing state is not a pass;
  - unavailable simulation is not a pass;
  - unsupported verification is clearly shown;
  - error details are useful to the learner;
  - no broad silent catch.

Scoring:
  - configuration correctness
  - reasoning/prediction
  - evidence quality
  - verification
  - safe change
  - documentation
  - reflection
  - hint usage as a learning signal, not a punishment

Do not make speed the main score. Offer untimed learning mode.


11. ENGINEER MODE
-----------------
Engineer Mode is ticket-based, not a static checklist.

Workflow:
  1. Read ticket.
  2. Confirm authorization and scope.
  3. Inspect topology and baseline.
  4. Define impact and affected users.
  5. Write two or more hypotheses.
  6. Collect evidence.
  7. Choose smallest safe change.
  8. Configure.
  9. Verify independently.
  10. Document root cause, rollback, and prevention.

Ticket types:
  - branch connectivity loss
  - VLAN isolation failure
  - DHCP outage
  - DNS resolution failure
  - route missing
  - ACL blocks approved service
  - SSH management unavailable
  - suspicious traffic investigation
  - change request with rollback

Engineer Mode must show:
  - ticket severity;
  - scope;
  - time window without forcing a timer;
  - allowed tools;
  - prohibited actions;
  - success criteria;
  - evidence rubric;
  - post-incident report.


12. SECURITY MODE
-----------------
Security labs must be authorized and isolated.

Every security lab includes:
  - rules of engagement;
  - exact synthetic target scope;
  - prohibited external targets;
  - default-deny network egress;
  - reset/teardown;
  - expected evidence;
  - defensive mitigation;
  - debrief.

Tracks:
  A. Security foundations
     Authentication, permissions, logs, network segmentation, secure management.
  B. Blue team
     Alert triage, PCAP, DNS anomaly, firewall logs, timeline, detection, IR.
  C. Safe offensive learning
     Only isolated synthetic targets, with scope and remediation.
  D. Network security
     ACL, port security, SSH, NAT boundary, VPN concepts.

Store ATT&CK technique ID and version only where the lab genuinely demonstrates
the technique. Do not pursue matrix coverage for its own sake.

18. SECURE INFRASTRUCTURE AND DEPLOYMENT
----------------------------------------
Browser simulation:
  - deterministic;
  - no host access;
  - bounded memory;
  - resettable;
  - testable in CI.

Container/VM/emulator workers:
  - separate worker service, never inside web process;
  - per-user or per-team ephemeral worker;
  - default-deny egress;
  - management network separated from learner network;
  - no host filesystem mounts;
  - CPU, memory, process, disk, and time quotas;
  - signed/scanned/patched images;
  - short-lived credentials;
  - snapshots and guaranteed teardown;
  - emergency kill/reset;
  - audit events;
  - image/license tracking.

Deployment environments:
  A. local development: frontend + backend.
  B. single-machine classroom: local catalog and browser simulation.
  C. hosted simulation: API, WebSocket, database/cache, worker pool.
  D. advanced range: isolated worker cluster with emulator/VM support.

Configuration:
  - environment variables for URLs and ports;
  - never commit secrets;
  - health endpoint;
  - readiness endpoint;
  - migration/version check;
  - graceful shutdown;
  - backup and restore;
  - rate limits;
  - authentication and role authorization before multi-user deployment.

PHASE 8 - DASHBOARD EXPERIENCE

Browser tests:
  - first-time beginner flow;

21. STUDENT PROBLEM MATRIX
---------------------------
Problem: "I do not know where to start."
  Fix: recommended path, first lab, beginner tutorial, visible next action.

Problem: "I typed the command but nothing makes sense."
  Fix: target device, mode prompt, expected state, explanation, verification.

Problem: "Topology and command do not match."
  Fix: canonical lab validator and step-to-device/interface references.

Problem: "Ping failed; I changed everything."
  Fix: hypothesis log and layer-by-layer troubleshooting checklist.

Problem: "The simulator says success but Packet Tracer differs."
  Fix: fidelity badge, capability matrix, production-difference panel.

Problem: "There are too many labs."
  Fix: guided curriculum, filters, prerequisite graph, curated first 20 labs.

Problem: "I cannot see which device is which."
  Fix: topology key, device role, interface table, text equivalent.

Problem: "I forgot what I changed."
  Fix: command history, before/after diff, evidence export, rollback.

Problem: "I have a slow computer."
  Fix: browser simulation, low-resource mode, no WebGL requirement for core labs.

Problem: "I am afraid to break something."
  Fix: isolated session, reset, snapshots, safe-failure labels, no host access.

Problem: "I cannot use the mouse or distinguish colors."
  Fix: keyboard navigation, focus indicators, text/icons, accessible diagrams.

Problem: "I learned commands but cannot solve a new problem."
  Fix: transfer labs, hidden faults, prediction, reflection, capstones.
